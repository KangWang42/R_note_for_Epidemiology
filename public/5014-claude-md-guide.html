如何写好一份 CLAUDE.md：让 AI 长期守规矩的项目规则

机器学习与AI
AI 工具
一份好的 CLAUDE.md 不是把所有想法堆进去，而是只留删掉会出错的规则。本文用”删除测试”“分层指针”“硬红线”三个支点，配合一份真实的流行病学科研 CLAUDE.md，讲清楚怎么写、怎么维护。
发布于

2026年6月16日

什么是 CLAUDE.md

CLAUDE.md 是 Claude Code 的项目记忆文件。每次会话启动时，它的内容会被自动注入上下文，成为 AI 在这个项目里始终遵守的规则与背景。它回答一个问题：「在这个项目里干活，有哪些事你必须知道、必须做、绝对不能做？」

它有两个层级：

  • 全局 CLAUDE.md（位于用户配置目录，如 ~/.claude/CLAUDE.md）：跨所有项目生效的个人规则。
  • 项目 CLAUDE.md（位于项目根目录）：只对当前项目生效，描述这个项目特有的约定。

写好它的回报是巨大的：AI 不再每次都要你重复「原始数据别动」「表格按论文顺序命名」「跑完要验证」，而是开箱就守规矩。写砸了同样代价明显：要么规则太空被忽略，要么规则太多把上下文撑爆、还互相打架。

注记本文的参照系

本文不空谈，而是以一份真实的、用于流行病学与生物统计研究的全局 CLAUDE.md（来自 EpiAgentKit）作为贯穿案例。它将跨任务分流、硬红线、单源指针和完成条件放在全局规则中，把领域细节下沉到对应 Skills。读完你可以按同样原则整理自己的版本。

一份好的 CLAUDE.md 长什么样

在动笔前，先建立判断标准。好的 CLAUDE.md 有五个可观察的特征：

特征 好 坏
密度 每条都是删了会出错的规则 充斥”尽量”“建议”“注意”等空话
长度 克制，多步流程下沉到别处 把完整教程、代码模板塞进来
可执行 规则具体、可被检验 模糊到无法判断有没有遵守
有优先级 冲突时知道听谁的 规则平铺、互相矛盾时无解
可维护 改一处、定期体检 越堆越多、从不删

一句话标准：CLAUDE.md 是红线清单与路由指针，不是知识库。它告诉 AI「边界在哪、该去哪查」，而不是把所有知识本身塞进来。

三个核心支点

写好 CLAUDE.md，记住三个支点就够了。

支点一：删除测试

这是最重要的一条。每写一条规则，都问自己：把它删掉，AI 会不会犯一个具体的、可观察的错误？ 会，就保留；不会，就删掉。

参照案例在文件开头就立了这条元规则：

> 维护原则：每条规则过"删除测试"——删了 Claude 会犯具体可观察的错误才保留。
> 目标 < 120 行；多步程序性内容一律下沉 skill，本文件只留规则与指针。

用删除测试一扫，大量「正确的废话」会被淘汰：

  • ❌「请编写高质量的代码」——删了 AI 也不会故意写烂代码，无信息量。
  • ❌「注意数据安全」——太模糊，无法检验，删了无影响。
  • ✅「NEVER 修改 01_data/rawdata/ 原始数据」——删了 AI 真的可能去改原始数据，必须留。

支点二：分层与指针下沉

CLAUDE.md 会占用每次会话的上下文，越长越贵、越容易被淹没。所以它只放每个 session 都要用的跨任务规则，多步骤的程序性内容下沉到 Skill（技能）里按需加载。

参照案例的做法是：CLAUDE.md 只留一张路由表，告诉 AI「遇到这类任务，去调用哪个技能」，具体怎么做写在技能文件里：

| 触发场景 | 必须调用 |
|---|---|
| 新建项目 / 初始化 | /project-init |
| 任意 R/Python 统计分析、回归、生存分析 | /r-biostats |
| 任意出图（ggplot / 论文图件） | /publication-figures |
| 写/改论文任一部件、投稿材料 | /academic-publishing |

这样 CLAUDE.md 始终轻量，而专业知识在需要时才被拉进来。判断标准：如果一段内容是「分多步怎么做」，它属于技能；如果是「必须/禁止做什么」的一句话约束，它才属于 CLAUDE.md。

支点三：硬红线与优先级

不是所有规则同等重要。把「违反 = 任务失败」的少数规则单独标成硬红线（CRITICAL），用强措辞（NEVER / 必须）写死，并给出一个明确的冲突优先级，让 AI 在规则打架时知道听谁的。

参照案例的优先级是这样定的：

## 规则优先级（冲突时）
1. 用户当轮明确指示
2. 本文件 CRITICAL 硬红线
3. 项目级 CLAUDE.md 项目特定规则
4. 已加载 skill 的执行流程
5. skill 内 DEFAULT / PREFERENCE / EXAMPLE

有了这个梯度，AI 不会因为「技能里的默认值」覆盖掉「用户当轮的明确要求」，也不会用次要偏好压过硬红线。

CLAUDE.md 与 Skills 的分工

这是新手最容易混淆的地方。两者职责截然不同：

CLAUDE.md Skill（技能）
加载时机 每次会话自动注入 任务匹配时按需加载
内容 红线、路由、优先级、背景 某类任务的完整执行流程
体量 越短越好（约 120 行） 可以很长、可带子文件
变化频率 低，稳定 随方法、模板更新
类比 公司员工手册的”总则” 各岗位的”作业指导书”

记法：CLAUDE.md 说「要不要做、能不能做」，Skill 说「具体怎么做」。把怎么做塞进 CLAUDE.md，文件会迅速膨胀且难维护；把红线丢进 Skill，又会因为技能不一定加载而失效。

结构骨架

一份成熟的全局 CLAUDE.md 可以参考下面的骨架（节选自参照案例）。注意它的每一节都对应一类「不写就会出错」的问题。

1. 工作方式（Approach）

开篇先定调：用什么口吻、什么交付标准、什么自检要求。

## Approach
- 写作以"我做了 X"研究者视角，不用 AI 助手口吻。
- 交付文本一律学术书面语；英文缩写首次出现给全称。
- 疑点 / 不一致 / 多个合理口径并存 → 先问用户再做，不擅自决定。
- 交付前强制自检（不等用户挑错）：发现一类问题立刻全文 grep 扫同类。
- 简洁输出；不堆开场闭场套话；不用 emoji。
- 不猜 API / 版本 / 包名；读代码或文档后再断言。

2. 路由表（自动义务）

把「什么任务该调什么技能」做成表，让 AI 无需用户点名就自动路由。

3. CRITICAL 硬红线

按主题分组的禁令与铁律，这是文件的核心。参照案例按「数据与路径」「代码编号」「结果与方法」「报错处理」「口径与表达」分组，例如：

### 数据与路径
- NEVER 修改 01_data/rawdata/ 原始数据。
- NEVER 用绝对路径；一律相对。
- NEVER 在项目根放临时 / 测试 / 零散结果。

### 结果与方法
- NEVER 写完代码不跑就宣称完成（实跑验证）。
- NEVER 只看 tail 几行就声明成功；必须全量扫 error/warning。

4. 目录骨架与工作流指针

一段目录树 + 关键工作流的去向，让 AI 知道东西该放哪、流程往哪走。

5. 优先级与记忆锚点

收尾放冲突优先级，以及一段「记忆锚点」——把最关键的几条规则再压缩复述一遍，降低被忽略的概率：

## 记忆锚点（删了会犯错的 5 条）
1. 02_code 编号连续 + 一次性脚本归档 → 否则脚本堆积失序。
2. Table/Fig 按论文行文编号，registry 单源 → 否则正文引用全错。
3. 结果变同步 results.yaml，方法变同步 DECISIONS.md → 否则数字源失锁。
4. 代码写完必跑 + 全量扫 error/warning → 否则交付带未验证错误。
5. 口径不明先问用户 → 否则分析方向偏离用户意图。

写作技巧

骨架之外，措辞决定规则到底有没有用。

  • 用强动词，不用软措辞：写 NEVER / 必须 / 一律，不写「尽量」「建议」「最好」。AI 对强约束的遵守度明显更高。
  • 每条红线带后果：「NEVER X → 否则会 Y」。后果让 AI 理解规则的分量，也方便你日后做删除测试。
  • 具体到可检验：不写「命名要规范」，写「主表命名 Table{N}_{描述}.xlsx，N 按论文行文顺序连续」。能被一眼判断对错的规则才有约束力。
  • 正例反例并列：对易错点给一组「✅ 这样 / ❌ 不这样」，比纯描述更不易被误解。
  • 把「先问」写进规则：凡是涉及判断（分组、终点、纳排、主分析方法），明确要求 AI 停下来问你，而不是替你猜。这是防止方向跑偏最省力的一条。
  • 用表格承载多分支：路由、优先级、对比这类「条件→动作」的内容，表格比段落更清晰、更省 token。

实战：从零写一份

假设你要给一个新的数据分析项目写 CLAUDE.md，可以按这四步走。

第一步：列错误清单。 先不写规则，先回忆「以前 AI 或自己在这类项目里踩过哪些坑」：改错了原始数据、文件名乱、结果改了忘同步、跑完没验证就说完成……每个坑就是一条候选规则的种子。

第二步：把坑翻译成红线。 每个坑写成一条「NEVER X → 否则 Y」或「必须 X」。这一步天然通过了删除测试，因为每条都对应一个真实发生过的错误。

第三步：分组与下沉。 把红线按主题分组（数据、代码、结果、表达）。凡是「分多步怎么做」的内容，抽出去写成技能，CLAUDE.md 里只留一行指针。

第四步：加优先级与锚点。 末尾补一段冲突优先级，再把最致命的 3-5 条压缩成「记忆锚点」复述一遍。完成后数一下行数,超出预算就回到删除测试再砍一轮。

实战：改进一份臃肿的 CLAUDE.md

如果你已经有一份越写越长的 CLAUDE.md，按这个顺序瘦身：

  1. 逐条做删除测试，删不掉的留下、删得掉的删。
  2. 揪出程序性内容（任何「第一步…第二步…」的段落）下沉成技能。
  3. 合并重复：同一主题散落各处的规则并到一节。
  4. 补优先级：如果还没有冲突优先级，加上。
  5. 复述锚点：把活下来的最关键几条做成记忆锚点。

常见错误

反模式 问题 纠正
当成知识库 把教程、代码模板全塞进来，文件臃肿 知识进技能/文档，CLAUDE.md 只留红线与指针
正确的废话 “写好代码”“注意质量”等无法检验 过删除测试，删掉无后果的条目
软措辞 满篇”尽量”“建议”，AI 容易忽略 关键项改成 NEVER / 必须
无优先级 规则冲突时 AI 行为不可预测 显式写出冲突优先级梯度
从不维护 规则过时、与实际脱节 定期体检，删过时项、补新坑
替用户做决定 口径不明时 AI 擅自选择 明确要求”口径不明先问用户”

维护

CLAUDE.md 不是写完就锁定的。它应该随项目一起演化：

  • 踩新坑就补一条：每次 AI 犯了一个本可避免的错，就考虑加一条对应红线——前提是它过删除测试。
  • 定期跑删除测试：每隔一段时间通读一遍，把不再触发错误的规则删掉，控制总长度。
  • 方法变了同步：项目的口径、流程变化时，对应规则与指针一起更新，避免规则与现实脱节。
  • 盯住长度预算：给自己定一个上限（如 120 行）。逼近上限就是一个信号——要么有内容该下沉成技能，要么有规则该删。

常见问题

Q：CLAUDE.md 应该多长？ 没有硬性标准，但越短越好。参照案例把全局规则控制在约 120 行。一旦超过，先问「是不是有程序性内容该下沉成技能」。

Q：全局和项目 CLAUDE.md 冲突了听谁的？ 一般「用户当轮指示 > 全局硬红线 > 项目特定规则 > 技能流程」。最好在全局文件里把这个优先级显式写出来。

Q：可以让 AI 帮我写 CLAUDE.md 吗？ 可以起草，但你必须亲自过删除测试——AI 容易写出一堆「正确的废话」，需要你按真实踩过的坑来筛选和加强。

Q：规则太多 AI 会不会记不住？ 会被稀释。这正是要做删除测试和记忆锚点的原因：把篇幅压下来，把最关键的几条额外复述一遍。

Q：CLAUDE.md 里能写代码吗？ 尽量不要写完整代码。可以放极短的命名约定、目录树、配置片段示例，但成段的实现代码应放到技能或项目文档里。
