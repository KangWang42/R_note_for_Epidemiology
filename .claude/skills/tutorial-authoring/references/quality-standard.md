# 教程质量标准

## 1. 教学目标

每篇文章只承诺一组清楚的学习成果。开头用一到两段回答：本教程解决什么问题、适合谁、读完能做什么。若需要前置知识、包版本、外部软件或数据结构，在第一次使用前说明。

不要用“完整教程”“从入门到精通”等标题代替范围。文章可以很长，但每一节都应推进理解、操作或判断；不能靠重复定义、堆函数清单和固定章节凑篇幅。

## 2. 段落与节奏

- 一个段落围绕一个中心判断展开，通常先给结论或问题，再解释原因、条件和后果。
- 复杂概念允许使用较长段落，前提是逻辑连续；不要把一句完整论证拆成多个两行短段。
- 列表用于并列条件、步骤和核对项，不把所有正文都改成项目符号。
- 表格用于稳定的一一映射或方法比较；需要论证、例外或时间顺序时用正文。
- 术语首次出现给出中文、英文全称和缩写；之后保持同一字面写法。
- 生活化类比只在能提高理解且不会扭曲定义时使用，并立即指出类比边界。

## 3. 事实与论断

- 区分定义、理论保证、经验规则、教学设定和作者建议。
- “稳健”“有效”“控制”“预测”“因果”等词必须写清成立条件。
- 不把固定阈值写成普遍真理。例如 SMD 0.1、插补次数、权重截断分位点和每变量事件数只能在有依据时作为启发式或敏感性设定。
- 软件版本、导出函数数、HTML 支持状态、安装方式和许可证属于会变化的信息，必须核对当前官方来源并标日期或版本。
- 观察性分析使用关联或在明确识别假设下的因果措辞；不写“证明”“等同随机试验”。

## 4. 代码与示例

- 最小示例先展示最少必要对象；完整示例再增加诊断、异常处理和报告。
- 每个关键代码块前说明它回答的问题，之后解释输出中的关键对象，而不是逐行翻译语法。
- 模拟数据要让暴露、协变量、结局、时间和删失关系与方法问题一致。若生成机制已知，明确它只用于教学核验。
- 函数名、参数名和返回字段以实际版本为准。所有展示为可运行的代码都要在相同环境实跑。
- 安装命令与分析代码分开。GitHub 包说明版本或提交锁定；不把非官方来源写成默认安装途径。
- 代码 warning 默认视为待检查证据。只有确认是无害库噪声后，才能在正文或构建记录中解释，不通过 `warning = FALSE` 掩盖真实问题。

## 5. 图件合同

候选图必须至少承担一种功能：展示数据分布、说明方法关系、暴露诊断问题、比较方案、呈现真实软件结果。只装饰页面的图不进入正文。

| 内容 | 正确来源 | 禁止做法 |
|---|---|---|
| 统计图、模拟结果、模型诊断 | 文章代码的真实输出 | 用生成式图片虚构数值或曲线 |
| 软件界面、文档页面、终端结果 | 实际运行或渲染截图 | 生成看似真实的假界面 |
| 流程、机制、框架 | `research-visuals` 规定的路径 | 因文字密集就直接手写模板 SVG |
| 科研原始图像 | 原始文件及允许的确定性处理 | 生成式重绘、补全或净化 |

正文应在图前说明读图问题，在图后说明观察到的模式与限制。替代文本描述图的结构和信息，不重复“下图展示”。

## 6. 文章结构

结构由任务决定，但通常应覆盖：

1. 问题、读者和学习目标；
2. 方法或工具定位及替代方案；
3. 假设、数据要求、版本或环境；
4. 最小可运行示例；
5. 完整工作流与诊断；
6. 输出解释、报告或交付；
7. 常见失败、边界与进一步资源。

不能要求所有文章具有相同标题。单一图形、单个函数或短操作教程可以更短；复杂因果、生存、缺失数据或样本量教程应给足方法边界和诊断。

## 7. 渲染与网页

- YAML 至少核对 `title`、`date`、`categories`、`description`；有 `image` 时路径必须存在。
- 二级标题形成目录，层级不能跳跃；代码 chunk 标签唯一且具有语义。
- 表格在移动端不截断关键列；长代码允许横向滚动或合理换行。
- 图中中文、图例、线型和颜色在实际显示尺寸下可读；不只依赖颜色传递信息。
- 本地相对链接和图片必须存在，外部链接指向支持该断言的页面。
- 定向渲染后同时扫描日志和最终 HTML；退出码为 0 不代表没有 warning、乱码或缺图。

## 8. 终审问题

- 删除任一章节、表或图后是否会损失必要理解？不会则删。
- 读者能否区分教学设置、软件输出和真实研究结论？
- 所有“应当”“通常”“控制”“当前”是否有条件或来源？
- 代码能否从空会话按文章顺序运行？
- 模拟是否真的体现方法要解决的数据结构？
- 图是否来自真实可追溯对象，且正文教会读者如何看？
- 是否报告适用边界、失败模式和不能由本方法解决的问题？
